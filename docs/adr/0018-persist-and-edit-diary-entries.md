# ADR 0018: Сохранение И Редактирование Записей Дневника

- Статус: принято
- Дата: 2026-09-25
- Область действия: локальные записи Дневника и edit bottom sheet

## Контекст

Сейчас Дневник строится из несогласованных с каталогом демонстрационных записей.
Добавления и Recent живут лишь до перезапуска; запись содержит отформатированное
количество и округлённые ккал, чего недостаточно для корректного редактирования.
Пользователь должен исправлять количество и приём пищи и удалять запись, не
теряя изменений после закрытия приложения.

## Решение

- Демо-записи убираются: в новом Дневнике нет вымышленной истории.
- Записи Дневника хранятся в существующей локальной SQLite-базе. Версия схемы
  увеличивается с v1 до v2 с протестированной Drift-миграцией, сохраняющей
  пользовательские продукты и их порции. Общий класс базы переносится в
  `lib/core/data/yam_database.dart`; репозитории остаются в своих features,
  физический файл базы `yam` не меняется.
- День хранится как локальная календарная дата `YYYY-MM-DD`, а `createdAt`,
  `updatedAt` и `deletedAt` — как отдельные UTC instants. Публичный ID записи —
  UUID v7, `deviceId` совпадает с ID установки. Удаление — soft delete.
- Запись содержит снимки имени, бренда, выбранного количества и единицы,
  доступных порций с их коэффициентами, питательности на базис и точных
  рассчитанных нутриентов. Каноническое количество — граммы либо миллилитры;
  коэффициент штуки задаётся явно. Данные каталога не пересчитывают историю,
  даже если исходный продукт изменён или удалён. Округление только для UI.
- Тап по любой реальной записи открывает компактный bottom sheet. Меняются
  количество/единица и приём пищи; виден предпросмотр КБЖУ. Название и БЖУ
  продукта не редактируются, дата остаётся выбранной в Дневнике. Кнопка
  корзины удаляет запись сразу, без подтверждения, с Undo. Изменение количества
  сохраняется только по нажатию «Сохранить»; закрытие отменяет несохранённый ввод.
- После добавления поиск остаётся открыт; запись отображается в Дневнике через
  локальный поток. «Недавние» — последние четыре разных продукта из реально
  сохранённых записей, в том числе после перезапуска; Undo удаления или
  добавления обновляет этот список. Отдельная таблица истории не нужна.
- Запись читается по сохранённым снимкам, а ссылка на исходный продукт
  используется только для повторного поиска. Встроенный каталог по-прежнему
  остаётся демонстрационным, цели и предпочтения — сессионными.

Это решение завершает ограничение ADR 0007/0012/0015 на in-memory записи и
Recent; контракт task-screen добавления, meal preselection, Undo и работа без
сети сохраняются. Для этого среза не добавляются новые зависимости и сервер.

## Проверка

До изменения схемы сохраняется экспорт v1. Проверяются миграция v1→v2 с
существующим пользовательским продуктом, сохранение записи после повторного
открытия БД, изменение количества и приёма, soft delete/Undo и точные
пересчёты для граммов, миллилитров и штуки. По разрешению пользователя
запускаются только прицельные тесты данных и расчётов; UI проверяется вручную.
