# ADR 0034: Обмен Базой Своих Продуктов В JSON

- Статус: принято
- Дата: 2026-10-31
- Область действия: «Мои блюда», Настройки, SQLite v6, backup v3

## Контекст

Пользователю нужен обмен только продуктами, отдельно от личной истории.
Базы должны создаваться вручную и через ИИ. Согласованы три режима:
полная замена, объединение без дублей и объединение с сохранением дублей.
Пользователь выбрал область только «Мои блюда» и ключ сравнения:
название + бренд + базис + КБЖУ.

## Решение

- Отдельный открытый формат: UTF-8 `.json`, `format: yam-foods`, `version: 1`,
  массив `foods`. Это не полный backup `.yam` и не raw SQLite.
- Экспорт содержит только активные UserFoods и их активные UserServings:
  название, категорию, бренд, описание, штрихкод, базис, точные КБЖУ и порции.
  UUID, метаданные установки, tombstones, избранное, дневник, вес, цели,
  встроенный каталог и OFF-кэш не экспортируются.
- Обязательные поля продукта: `name`, `category`, `unit` (`g`/`ml`),
  `basisAmount`, `kcal`, `protein`, `fat`, `carbs`. Базовое количество положительно,
  нутриенты конечны и неотрицательны. Калории сохраняются явно, без пересчёта
  по БЖУ. Это не меняет расчёт калорий в форме ручного создания ADR 0017.
- Необязательные поля: `brand`, `barcode`, `description`, `displayBasis`,
  `servings`. Штрихкод — строка цифр. Nullable-поля допускают отсутствие/null.
  Дополнительные поля игнорируются. Неизвестная версия отклоняется.
- `displayBasis`: `per100` при `basisAmount: 100` либо `perServing`;
  при отсутствии базис 100 считается на 100 г/мл, другой — на порцию.
  Порции задаются через `unit` (`serving`, `piece`, `glass`, `scoop`),
  положительный `baseAmount` в канонических г/мл, необязательный положительный
  `defaultAmount` (1 по умолчанию) и необязательный `label`.
  Недостающий эквивалент базиса `perServing` создаётся автоматически.
- Каждый добавленный продукт и каждая порция получают новые UUID v7,
  creation/update UTC metadata и deviceId текущей установки. Импортированные
  продукты доступны для правки и удаления в «Моих блюдах», как созданные вручную.
- **Заменить**: одной транзакцией soft-delete активных своих продуктов и порций,
  затем добавление всех продуктов файла, включая повторы. Прежние tombstones
  сохраняются. Пустой массив очищает только «Мои блюда». Перед применением —
  отдельное явное подтверждение; отмена ничего не меняет.
- **Объединить без дублей**: существующие продукты не изменяются. Ключ —
  название и бренд после trim/схлопывания пробелов/lowercase, каноническая
  единица, точное базовое количество и все четыре значения КБЖУ. Отсутствующий
  и пустой бренд равны. Никакого fuzzy matching, округления и пересчёта мл в г.
  Сравнение с активной базой и внутри файла; первая входящая запись сохраняется.
  Категория, штрихкод, описание и порции в ключ не входят: у совпадения остаётся
  существующий продукт со всеми своими полями. Ранее существовавшие дубли
  автоматически не удаляются. Удалённые продукты совпадениями не считаются.
- **Объединить с дублями**: добавление каждой входящей записи; повторный импорт
  создаёт ещё одну полную копию, включая совпадающие штрихкоды.
- В обоих объединениях дневник, цели, вес, RemoteFoods и installation identity
  не меняются. Замена имеет те же границы. Diary snapshots остаются прежними.
- Полная проверка до записи; кодек работает вне UI isolate. Лимиты: 64 МиБ,
  50 000 продуктов и 250 000 порций. Ошибка известного поля содержит JSON-путь,
  но не содержимое файла. Применение атомарно с rollback.
- Настройки получают отдельную секцию базы продуктов: экспорт, импорт,
  предпросмотр количества, выбор режима, результат и описание формата с
  копируемым примером. Файлы выбираются/сохраняются системным `file_picker`.
  Новых зависимостей нет; UI локализован RU/EN.

### Штрихкоды И Полные Резервные Копии

- SQLite v6 снимает UNIQUE со штрихкода UserFoods, не теряя строки, порции и
  метаданные. Поиск штрихкода не предполагает единственного совпадения.
  Ручное создание/изменение штрихкода по-прежнему предотвращает конфликт с
  другим активным продуктом; неизменённый штрихкод импортированного дубля
  не блокирует правку остальных полей.
- Старые `.yam` v1/v2 не допускают повторяющиеся штрихкоды. Экспорт полных
  копий переходит на v3, чтобы старое приложение явно отклоняло несовместимую
  копию. Импорт читает v1/v2/v3; в v3 повторы разрешены. Консервативная
  семантика дополнения полного backup по ID/занятому штрихкоду остаётся прежней.

Этот ADR **заменяет** UNIQUE-инвариант штрихкодов ADR 0016 и правило поколения
экспорта backup v2 ADR 0028/0030. Обязательная уникальность ID, история,
границы полного backup и остальные требования прежних ADR сохраняются.

## Проверка

Roundtrip точных чисел и порций; все три режима, повторные импорты, совпадения
внутри файла, регистр/пробелы, разные бренды/базисы/КБЖУ; сохранность дневника,
других таблиц и установки; атомарный отказ повреждённого файла; миграции
v1–v5→v6 и полный backup v1/v2/v3. Нативный runtime проверяет пользовательские
действия, отмену, предпросмотр и результат. Фактическая проверка и ограничения
фиксируются в PROJECT_STATE.
