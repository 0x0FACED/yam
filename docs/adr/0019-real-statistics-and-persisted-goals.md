# ADR 0019: Реальная Статистика, История Веса И Целей

- Статус: принято
- Дата: 2026-09-25
- Область действия: `/statistics`, онбординг, цели и вес в Дневнике/Настройках

## Контекст

`yam_statistics.html` описывает реальные тренды питания и веса, но в SQLite v2
есть лишь записи Дневника и продукты. Вес и цели сейчас сессионные, а числа
первого онбординга взяты из макета. Они не могут становиться данными статистики.

## Решение

- Экран следует составу и плотности `agents/design/yam_statistics.html`:
  периоды 7/30/90/365 дней и «Всё», компактная сводка, вес, калории, средние
  БЖУ, регулярность и частые продукты. Нет подставленных рядов графиков.
  Текущая статистика считается по локальным снимкам записей Дневника;
  отсутствие истории показывается пустым состоянием.
- В SQLite v3 добавляются `weight_entries` с точными кг и локальным днём
  измерения отдельно от UTC instant, и `goal_versions` с датой начала действия,
  kcal, БЖУ, целью веса и типом цели. Сохраняются UUID v7, metadata, deviceId,
  soft delete и индексы запросов. В один локальный день действует последняя
  версия цели за этот день. Записи до первой цели не получают её задним числом.
  Миграция v2→v3 сохраняет продукты и Дневник и проверяется отдельно.
- При первом открытии онбординга нет демо-предзаполнения веса и целей. При
  повторном открытии используются сохранённые значения. Завершение атомарно
  сохраняет версию целей и первое/изменённое взвешивание на сегодняшний локальный
  день; неизменный вес не дублируется как якобы новое измерение;
  отмена ничего не меняет. Onboarding по-прежнему запускается из Настроек и
  не навязывается при старте. Цели и текущий вес загружаются из SQLite и сразу
  обновляют Settings, Diary и Statistics. Тема остаётся сессионной.
- Текущий вес — последнее сохранённое измерение, а не отдельная копия в
  профиле. На графике показаны фактические измерения (не интерполированные
  значения); при нескольких измерениях за день берётся последнее. Изменение
  веса за период считается между первыми и последними доступными точками;
  при недостатке точек динамика не показывается. В карточке веса есть
  компактное действие записи/правки веса и даты, удаление обратимо через Undo.
- Средние ккал и БЖУ считаются по дням с дневными записями. Незалогированные
  дни не приравниваются к нулю. «День в цели» — день с едой и действовавшей
  на эту дату целью kcal, когда точное потребление находится в диапазоне
  90–110% этой цели включительно. Ниже — недобор, выше — превышение;
  дни без цели исключаются из знаменателя. Цвета статусов берутся из
  `AppSemanticColors.goalBelow/Within/Above`, цвета БЖУ — только из macro tokens.
  Средние БЖУ сравниваются со средними историческими целями только если цель
  существовала во все дни с едой выбранного периода.
- «Всё» начинается с первой реальной записи питания или веса. Для длительных
  периодов калории группируются по неделям/месяцам как среднее за дни с едой,
  с явной подписью; нет искусственных нулевых столбиков. Тепловая карта
  показывает последние не более 30 календарных дней выбранного периода
  с явной подписью окна; сводка периода охватывает весь выбранный диапазон.
  Частые продукты сгруппированы по foodId с числом разных дней и средним
  каноническим количеством, без выдуманных рекомендаций.

Это решение **заменяет** в ADR 0013 сессионное хранение профиля и исходные
числа онбординга из макета; шаги, motion и запуск из Настроек сохраняются.
Уточняет ADR 0009 только в части отображения целей и веса: сохранение темы,
единиц, языка, экспорта и прочих настроек не добавляется.

## Проверка

Миграция v2→v3 с сохранёнными дневными записями; точечные проверки агрегации
по дням, пустых дней, смены цели и порога ±10%, повторного открытия веса/целей.
UI — ручная проверка по макету в RU/EN и обеих темах; без набора goldens.
