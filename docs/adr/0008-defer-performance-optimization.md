# ADR 0008: Отложить Performance-Оптимизацию До Реальной Проблемы

- Статус: принято
- Дата: 2026-09-20
- Заменяет: ADR 0006

## Контекст

На этапе визуального MVP обязательные profile-бенчмарки, бюджеты кадров и
привязка к reference-устройству создают процессную нагрузку раньше, чем у
продукта появились реальные данные и подтвержденные проблемы
производительности.

## Решение

- У YAM нет числовых performance-бюджетов и обязательных profile-прогонов на
  этапе MVP.
- Производительность исследуется и оптимизируется после появления
  воспроизводимой пользовательской проблемы или измеримой деградации.
- Сохраняются только базовые инженерные ограничения: не блокировать локальный
  UI сетью, не запускать тяжелую работу из `build` и использовать ленивые
  списки для действительно неограниченных коллекций.
- Отдельная benchmark-инфраструктура для дневника удаляется.

## Последствия

- UI-срезы проверяются форматированием, анализатором и обычными тестами
  корректности без обязательного измерения миллисекунд.
- Кэширование, isolates, специальные performance-пакеты и микрооптимизации не
  добавляются без наблюдаемой необходимости.
- Если появится заметный лаг, для него сначала создается воспроизводимый
  сценарий, а затем выбирается минимальное исправление.
