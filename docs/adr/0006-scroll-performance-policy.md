# ADR 0006: Политика Производительности Прокрутки

- Статус: принято
- Дата: 2026-09-18

## Контекст

На Android-устройстве с экраном 120 Гц дневник формально укладывался в бюджет 60 Гц, но давал заметные рывки. Profile benchmark показал raster p99 `12.421 ms` при бюджете кадра 120 Гц `8.33 ms`. Периодические пики совпадали с отрисовкой стандартного Android `StretchEffect` на границах списка; весь compact-дневник также находился в одном `SliverToBoxAdapter` и строился заранее.

## Решение

- Приложение использует `AppScrollBehavior`, который отключает визуальный overscroll indicator, включая дорогой Android stretch effect, но сохраняет платформенные scroll physics и жесты.
- Неограниченные растущие списки строятся ленивыми slivers; большой `Column` внутри одного `SliverToBoxAdapter` для таких экранов не используется.
- Критичные сценарии прокрутки проверяются в profile mode на реальном устройстве. Для reference-устройства с экраном 120 Гц p99 build и raster должны быть ниже `8.33 ms`, а счетчики кадров, пропустивших стандартный Flutter frame budget, должны быть нулевыми.
- Performance-сравнения выполняются одним сценарием на одном устройстве; результаты разных устройств напрямую не сравниваются.

## Последствия

- Android glow/stretch не отображается; граница контента остается очевидной по остановке прокрутки.
- Новые длинные экраны должны использовать `SliverList`, `ListView.builder` или эквивалентную ленивую композицию.
- `integration_test/diary_scroll_performance_test.dart` является первым regression benchmark и запускается через `flutter drive --no-dds` в profile mode.
- После изменения дневника benchmark нужно повторить на reference-устройстве и сравнить `build/integration_response_data.json` с последним зафиксированным результатом.
