# ADR 0031: Версионный Changelog И Заметки GitHub Release

- Статус: принято
- Дата: 2026-10-26
- Область действия: `CHANGELOG.md`, релизный CLI, GitHub CI/release

## Контекст

Пользователь хочет вести историю изменений в репозитории и показывать изменения
каждой версии в её GitHub Release. Сейчас описание релиза содержит только
инструкции к пакетам. Дублировать пользовательские заметки в workflow или
получать их из необработанных сообщений коммитов не нужно.

## Решение

- `CHANGELOG.md` — единственный источник пользовательских заметок. Формат основан
  на Keep a Changelog 1.1.0: `Unreleased` сверху, затем версии от новых к старым,
  ISO-даты и группы Added/Changed/Deprecated/Removed/Fixed/Security по необходимости.
  Текст заметок — русский; пустые группы не создаются. Записываются изменения,
  важные пользователю, включая совместимость данных и условия обновления.
- Формат заголовков: `## [Unreleased]` и
  `## [MAJOR.MINOR.PATCH] - YYYY-MM-DD`. Версия без `v`/build suffix соответствует
  pubspec; тег остаётся `vMAJOR.MINOR.PATCH`. Перед тегом владелец переносит
  накопленные пункты Unreleased в датированный раздел версии, оставляя Unreleased
  для следующих изменений. Запись в changelog сама по себе релиз не публикует.
- История начинается с фактической v0.1.0 и подготовленных заметок v0.2.0.
  Неизвестные старые версии/даты не придумываются. Уже выпущенные записи не
  переписываются ради нового релиза; исправлять фактические ошибки допустимо.
- Извлечение живёт в небольшом Dart-модуле релизного инструмента, без новой
  зависимости/action и без shell-разбора Markdown. Поддерживается оговорённая
  структура Keep a Changelog: точные H2-заголовки версий, Markdown тела,
  fenced blocks/комментарии и однострочные reference definitions.
- CLI `tool/release_metadata.dart` проверяет changelog и версию. При `--tag`
  обязателен непустой раздел именно этой версии, без fallback на Unreleased
  или последний заголовок; `--notes-file PATH` записывает его Markdown в файл.
  Неоднозначные/неверные заголовки, повторные версии, неверные даты и пустые
  выпущенные разделы дают ошибку до платформенных сборок. Reference definitions
  сохраняются для корректного отображения ссылок в извлечённых заметках.
- CI на push/PR проверяет структуру changelog без требования выпускать новую
  версию для каждого коммита. Release prepare дополнительно сопоставляет тег,
  pubspec и раздел changelog и передаёт проверенный файл через отдельный artifact.
  Publish использует этот файл того же tagged commit через `gh --notes-file`.
  Содержимое Markdown не подставляется в shell или многострочные GitHub outputs.
- Инструкции Android/Linux/macOS и SHA256SUMS остаются статическим дополнением
  после заметок версии. Не добавляется автоматический git-log/PR changelog,
  conventional-commit политика, release bot, автокоммиты, теги или публикации
  со стороны агента. Прежние подписи, проверки и draft-before-assets сохраняются.

Этот ADR дополняет ADR 0005/0025: их версия/подпись/артефакты не меняются,
а описание GitHub Release становится версионным и проверяемым.

## Рассмотренные Альтернативы

- GitHub `--generate-notes`: полезен при принятой политике PR/labels, которой
  здесь нет; это не замена редактируемым пользовательским заметкам.
- Positional extract-action: рассмотренный ffurrer2/extract-release-notes берёт
  содержимое между вторым и третьим H2, а не раздел заданной версии. Для строгой
  связи tag/pubspec/notes и SHA-pinned pipeline лишняя зависимость не нужна.
- `sed`/`awk` в workflow: правила версий и Markdown размазываются по shell,
  труднее проверить неоднозначные заголовки и границы секций.

## Источники И Проверка

- https://keepachangelog.com/en/1.1.0/
- https://cli.github.com/manual/gh_release_create
- https://github.com/ffurrer2/extract-release-notes

Проверяются точный выбор версии/границы, Markdown/fences/ссылки, отсутствующие,
пустые и дублированные записи, неверные даты, реальные CLI-команды с output file
и GitHub outputs. Workflow проходит actionlint; локальная проверка не создаёт
GitHub Release и не подменяет фактический runner-прогон.
