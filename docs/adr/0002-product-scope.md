# ADR 0002: Продуктовый Scope И UX-Принципы

- Статус: принято
- Дата: 2026-09-15
- Обновлено: 2026-09-20
- Приоритет: этот ADR заменяет конфликтующие продуктовые и MVP-решения
  из `agents/PROJECT_BLUEPRINT.md`. Архитектурные и data-решения blueprint
  остаются в силе, если не superseded отдельным ADR.

## Контекст

YAM должен быть прежде всего быстрым ежедневным трекером питания.

Главный продуктовый риск — постепенно превратить приложение в большой
fitness-комбайн, где редкие возможности мешают самому частому действию:
быстро записать съеденную еду.

Поэтому необходимо зафиксировать основные продуктовые границы и UX-принципы,
но не превращать ADR в подробную спецификацию каждого экрана.

## Решение

### Основная навигация

На compact layout существуют три основных раздела:

1. Дневник
2. Статистика
3. Настройки

Добавление еды — contextual action дневника, а не отдельный раздел навигации.

Adaptive navigation определяется ADR 0004.

### Главный UX-принцип

YAM оптимизируется не под первое использование, а под регулярное.

Повторное добавление уже известного продукта должно требовать минимального
количества действий.

Приоритет:

- часто используемые продукты;
- недавние продукты;
- запомненные порции;
- быстрый add;
- Undo после обратимых действий.

Редкие функции не должны усложнять основной workflow.

### Добавление еды

Вход через конкретный meal section заранее определяет приём пищи.

Быстрое добавление продукта с известной последней порцией выполняется
без обязательного промежуточного подтверждения и сопровождается Undo.

Тап по самому продукту открывает редактирование количества/порции.

Удаление одиночной diary entry выполняется сразу с Undo.

Confirmation используется только для высокорисковых или массовых
необратимых действий, например удаления всех данных.

### Onboarding

MVP onboarding состоит из трёх коротких шагов:

1. Цель:
   - снизить вес;
   - поддерживать вес;
   - набрать вес.

2. Вес:
   - текущий вес;
   - целевой вес.

3. Цели питания:
   - kcal;
   - белки;
   - жиры;
   - углеводы.

На этом этапе onboarding не требует:

- пола;
- возраста;
- роста;
- activity questionnaire;
- желаемого недельного темпа;
- автоматического расчёта нормы.

Все введённые цели можно изменить позже через Settings → Goals.

Автоматический расчёт целей может быть добавлен отдельным последующим
product decision и не является обязательной частью MVP onboarding.

### Goals

Пользователь может вручную задавать:

- дневную цель kcal;
- белки;
- жиры;
- углеводы;
- текущий вес;
- целевой вес.

Ручные значения являются допустимыми независимо от наличия будущего
автоматического калькулятора.

### Темы

Поддерживаются:

- System;
- Light;
- Dark.

Light и Dark являются полноценными темами, а не вторичной адаптацией
одной основной темы.

### Не входит в основной MVP UX

Следующие возможности не должны появляться без отдельной продуктовой задачи:

- social;
- achievements;
- streak gamification;
- AI coach;
- generated meal plans;
- обязательный account;
- subscription/paywall;
- fitness-score или оценка "правильности" питания.

Более поздние возможности blueprint не считаются обязательными только
из-за присутствия в долгосрочном roadmap.

## Что этот ADR намеренно не определяет

Этот ADR не является каталогом всех экранов.

Он не фиксирует:

- конкретный layout;
- текст каждой подписи;
- точные поля будущих advanced features;
- полный roadmap;
- точный visual design.

Visual contract находится в design documentation и approved screen references.

Архитектурные/data решения находятся в соответствующих ADR и blueprint.

Текущее состояние реализации находится в `agents/PROJECT_STATE.md`.

## Последствия

Новые feature ideas не должны автоматически попадать в MVP.

При реализации UI агент сначала сохраняет описанные здесь workflow,
а затем следует approved visual references.

Изменение перечисленных выше продуктовых принципов требует отдельного
явного решения, а не локальной импровизации внутри feature implementation.
