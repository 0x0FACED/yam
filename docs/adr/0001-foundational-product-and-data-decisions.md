# ADR 0001: Базовые Решения По Продукту И Данным

- Статус: принято
- Дата: 2026-09-15
- Источник: `agents/PROJECT_BLUEPRINT.md`, разделы 2, 3, 7-10, 32-35, 45, 59-64 и 70.

## Контекст

YAM должен быть полезным offline в первый день использования, сохранять корректные исторические данные о питании и развиваться до optional multi-device sync без переписывания клиента при появлении backend. Эти ограничения влияют на client, data model и UI с первого slice реализации.

## Решение

- Flutter -- клиентский стек. Riverpod, `go_router` и Drift/SQLite являются планируемыми основами application, routing и persistence.
- SQLite -- локальный source of truth. Network providers только обогащают локальный каталог и никогда не блокируют основные workflow дневника.
- Внешние и встроенные данные продуктов нормализуются в одну внутреннюю модель еды до использования приложением.
- Записи дневника хранят снимки имени продукта, бренда, количества, единицы и нутриентов. Изменение источника продукта не может изменить записанную историю.
- Public ID пользовательских сущностей используют UUID v7. Persisted sync-relevant entities поддерживают metadata и soft-delete требования из blueprint.
- Дни дневника являются локальными календарными датами. Instants и presentation rounding отделены от domain values.
- Канонические единицы хранения: grams, milliliters, kilograms и kcal. Конвертация и отображение происходят на границе UI.
- Весь видимый пользователю UI copy использует generated Flutter l10n. Исходные locale: русский и английский.
- UI должен быстро отображать локальные данные и адаптировать навигацию и layout к компактным и широким form factor. Reusable visual tokens и motion централизуются до роста feature UI.
- Разработка идет через local MVP до remote search, barcode scanning, аккаунтов, backend или sync.

## Последствия

- Изменения схемы БД требуют Drift migration и migration tests.
- Расчеты нутриентов находятся в domain или application коде с unit tests, а не в widgets.
- Feature work должен сохранять local operation, стабильные снимки дневника и отзывчивый ввод до добавления optional integrations.
- Последующие решения, включая конкретные theme tokens, детали схемы БД, разрешение конфликтов sync и food-provider API, требуют отдельных ADR, когда станут активной задачей.

## Отклоненные Пока Альтернативы

- Server-first владение данными или обязательный аккаунт.
- Прямые ссылки на remote food в записях дневника.
- Одна универсальная модель измерений граммов и миллилитров.
- Hardcoded UI copy и mobile layout, растянутый на desktop-окна.
